# Devlog 081 — Save Files: The Player's Persistent State

## Goal

Arc 7's last system: persistence. A versioned `save.dat` in the project folder holding everything that belongs to the *player* — campaign progress, Gold Rush best times per seed, Temple Run's best height, and per-player settings — loaded at boot and written at the moments progress happens.

## Concept

- **Three files, three owners.** The engine now has a clean separation a new user can be taught in one breath: `project.myengine` is the *game* (its identity, levels, seed), `engine.ini` is the *machine* (window size, volume, speed), and `save.dat` is the *player* (what they have done and how they like it). Anything new that persists now has an obvious home, and the wrong-home mistakes (progress in the game's card, a preference in the machine's ini) have somewhere better to go.
- **The save stores the campaign whole — levels included.** `save.campaign` is the full Campaign model, level list and all. That looks redundant next to the project card, and it is the point: on load, the runtime compares the saved list against the project's current one, and only restores progress when they match. A game whose levels were edited since the save was written starts fresh instead of restoring flags onto the wrong levels — the save describes a campaign that may no longer exist, and says which one it meant.
- **Writes happen at the moment, not at exit.** Progress persists when a Goal is touched, a run is won, a climb ends in a new best, a campaign is reset, a preference flips — never "on quit," because quits are exactly the path that loses things (crashes, closed laptops, killed processes). Each write is the whole small file; at this size, atomicity theatre would cost more than it protects.
- **Bests only move one way.** `recordTime` and `recordHeight` return whether the result *was* a new best, and only then does the runtime persist and celebrate ("New best time!" on the Won screen, the best shown beside the run's own number from then on). A worse result changes nothing on disk — the file is a record of peaks, not a log of attempts.
- **Refusals are whole, ignorance is partial.** A `format=` other than 1 refuses the file entire (the Project rule). Unknown *keys* inside a format-1 file are ignored — a newer save read by an older build keeps what it understands. A missing file is not an error at all: it is every player's first run.
- **A player save is not game data.** `save.dat` joins `.gitignore`: it is generated by playing, differs per player, and would dirty every checkout it touched. The demo projects ship without one; yours appears when you play.

## Code built

- `src/SaveData.hpp` / `src/SaveData.cpp` (new, in GameLib) — the `SaveData` model (campaign, per-seed best times, temple best, settings map; `recordTime`/`recordHeight` best-only semantics) and the format-1 text load/write pair, root-aware like Project's.
- `src/runtime_main.cpp` — boot restore (with the level-list match), a single `persist()` the progress moments call (Goal completion, campaign reset, new bests, the shake toggle), best-aware Won/Caught score lines with the celebration line, and the per-player shake preference itself: **K on the title screen** toggles camera shake, its state shown on the seed line, applied at the camera, stored under `setting.shake` — the settings map's first real citizen.
- `.gitignore` — `save.dat`.
- `tests/tests_main.cpp` — the save check (suite now 59).

## Verification

- Harness: **59 passed, 0 failed** — a full round-trip through a real file (campaign flags and current, a best time to the centisecond, temple best, a setting plus its fallback), worse results refused by both record functions, a `format=99` file refused whole with the output untouched, and a missing file reading as an ordinary first run.
