# Devlog 079 — Campaign Structure: Levels, Progress, a Finish Line

## Goal

Lesson 78 gave a project many scenes and doors between them. This lesson gives the journey a *shape*: an ordered campaign over the project's level list — which levels are done, which is next, what "finished" means — plus the finish line itself, an entity named Goal, and the runtime flow that plays a campaign from title screen to completion.

## Concept

- **The campaign is a model, not a screen.** `Campaign` is pure state and rules: the level list (the project's own `scenes`, in order), a parallel completed flag per level, and `current`, the level in play. No files, no graphics — hosts present it, Game feeds it, and Lesson 81's save file will persist it. Putting progression in a struct instead of the runtime's loop is what lets three different consumers share one truth.
- **Unlocking is the genre's standard rule.** Level 0 is always open; level *i* opens when level *i−1* is completed. `complete()` marks a level done and moves `current` to the *next uncompleted* level — which is why replaying an earlier level and finishing it again doesn't rewind progress: `current` always recomputes from the flags, never just increments. The model is deliberately permissive (any index may complete — a host could allow a secret level); hosts gate *entry* with `isUnlocked()`.
- **A finish line is a name, like a door.** Completion had to come from the world, not from a menu: an entity named `Goal`, touched exactly the way Lesson 78's Exits are touched, latches `goalTouched()` in Game. The symmetry is the point — an author who learned doors already knows goals. Scene loads clear the latch; the runtime answers it by recording the completion and travelling onward to the next uncompleted level, landing on its `Spawn:<from>` like any other arrival.
- **Doors and goals coexist.** Exits remain free travel (wander back any time; the runtime keeps the campaign's "level in play" synced when a door is used), while Goals are progression. A level can have both — the demo's room 1 does.
- **The demo is data.** `games/two-rooms/` is a complete two-level campaign generated by the engine's own APIs (createProjectFolder, saveScene, saveProject): room 1 with a Goal and a door, room 2 with a named landing, a default landing, and its own Goal. It exists so the campaign can be *opened in the editor and played*, not just unit-tested — and the harness checks its card lists both levels whenever it runs from the repo root.
- **The level select is plain text — on purpose.** The roadmap's widget lesson is next, and it will rebuild this title screen from shared UI widgets. Shipping the flow first, in the runtime's existing text style, keeps the campaign's behaviour independent of the widgets' arrival: Lesson 80 changes how the screen is *built*, not what it *does*.

## Code built

- `src/Campaign.hpp` / `src/Campaign.cpp` (new, in GameLib) — the model: `reset`, `isUnlocked`, `isCompleted`, `complete` / `completeCurrent`, `nextLevel`, `finished`.
- `src/Game.hpp` / `src/Game.cpp` — the Goal latch (`goalTouched` / `clearGoalTouched`), checked beside the Exit check in `update()`, cleared by scene loads and fresh ascents.
- `src/runtime_main.cpp` — campaign mode (a scene-mode project with 2+ listed scenes): title level select (Up/Down among unlocked levels, Enter enters the chosen level fresh at its default Spawn), the Goal answer (complete → travel or Campaign Complete screen), Exit travel syncing `campaign.current`, the campaign HUD line ("Level N of M"), and the Campaign Complete screen (Enter: title; R: fresh campaign).
- `games/two-rooms/` — the demo campaign project (card + two scene files), generated by probe with the engine's own APIs.
- `tests/tests_main.cpp` — the campaign check (suite now 57), including the demo-card clause.

## Verification

- Harness: **57 passed, 0 failed** — unlock gates in order (0 open, 1 and 2 shut), completion marching `current` forward, a replayed completion not rewinding, `finished()` only when all flags are set, `complete(7)` refused; and through real scene files: a Goal staged on the player latches in one update and a load clears it.
- Probe: the whole campaign played at the Game+Campaign level — room 1's Goal touched, `current` 0 → 1, arrival in room 2 at exactly Spawn:room1 (120, 500), room 2's Goal touched, `finished()` true. The demo project itself was generated by the same run, through the public APIs a game's own tooling would use.
